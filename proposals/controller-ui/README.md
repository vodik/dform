# The controller UI, a mock

One self-contained page, `controller.html`: a clickable mock of what dform's controller UI could be, built 2026-10-15 to bootstrap the design, not to commit to. Open it in a browser; its design note and critique are the comment at the top of the file.

The frame it settled on: the primary screen is the estate (entities, relationships, health and the four-source reading on each node), an estate is one key value (`env=lab`), its stacks the lanes, the instances it reaches the regions, and a project is the set of its estates; the plan is a propagation overlay; no lines at rest and none for propagation (a reached node is tinted with its hop count), position is dependency, a selected node's direct edges the only lines; the right column shows the resource's document as the plan prints it, with sources per key and the four-source reading per attribute, `why` on the attribute; progressive disclosure (a card is its state, the reasons are the hover's `why`); the controller's clock is events and runs, ticks only inside a run; the levers are the controller's real ones (sign, approve a drift revert); no sync button, no red-amber-green. It is not Argo's object tree ("where does it live") but "what depends on what, what is wrong, where would a change go".

The data is the three estates under examples/, terry.org's release system, and the user's own project. A Query tab takes a dform query and answers a table with `why` on every row; a saved query is a Data view; a query can light the estate. Every node opens on the same panel; a value the program files do not hold is shown as a placeholder chip, never invented; the sidebar shows only facts the model holds, never commentary. Run numbers, digests and times are the mock's own state.
