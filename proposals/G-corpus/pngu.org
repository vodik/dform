* Notes

** Lowering, where it is not obvious

- The =when env(Env) { ... }= wrapper is gone: it only existed to bind =Env=
  for every statement inside. Every statement in it read at least one
  setting, so each still gets exactly one =env(E)= literal, now from =cfg=.
  Literal order differs (the guard was appended last); plans and strata do
  not depend on body order.
- ="projects/{cfg.project_id}/global/networks/{cfg.network_name}"= is a
  =format= term in the field value where today's rule binds =NetId= by an
  equality in the body. Same value, same predicates.
- =dashboard_json = file.json["examples/files/dashboard-pngu.json"]= is the
  extern literal =file.json("examples/...", Dash)= in the body.
- =for ip = "pngu-grpc"= keeps today's =IpName= binding so the name is
  ="static-ip-{ip}"=, a =format= appended last, as today.
- =output project_id = cfg.project_id= needs a read, so it lowers to the
  rule =output(project_id, V) :- env(E), setting(E, .project_id, V)=, today's
  form; =output k = t= without reads stays the =Stmt::Output= fact.
- =peering{ env: env, name: name, peer_network: peer }= reads the input =env=
  into the record's =env= field: =env(E), peering{env: E, ...}=.

** Reads better

- This is the file the change is for: 26 read-carrier variables to none.
  =project = cfg.project_id= replaces a variable per setting and a
  =setting(Env, .project_id, ProjectId)= line per resource (7 resources ×
  up to 8 settings lines).
- The one constraint is one line and says its path once.

** Reads worse

- The network id interpolation is repeated three times; the Prolog form
  repeated a =format= and a binding three times too, but the new form makes
  a value rule (=net_id = "projects/..."=) so tempting that stage 2 will get
  asked for it, and it adds a predicate (a strata change).
- =cfg= hides that every field is a join on =env=; a reader who wants to
  know "what does this resource depend on" must know =let= is textual.
