#+TITLE: dform on OVH Public Cloud, worked through
#+STARTUP: overview

A worked example in today's surface syntax (docs/grammar.md, edition
2026): a private network, OVH Managed Kubernetes (MKS) on it, an app on the
cluster, and continuous delivery by the in-cluster controller. The last
part is the interesting one: changing the cluster while it runs, with the
controller living on it.

*None of this runs today.* It parses against the grammar as it stands, but
three pieces do not exist yet, and the text marks every place it leans on
one of them:

- *An OVH provider.* The shortest route is the parked Terraform bridge over
  =ovh/ovh=; types below keep that provider's resource names under an
  =ovh.= namespace (=ovh_cloud_project_kube= is =ovh.cloud_project_kube=).
  Part 1 lists the schema facts the example assumes.
- *A kubeconfig as a secret credential.* MKS returns one sensitive
  kubeconfig, not an endpoint and a CA; the Kubernetes provider must accept
  it through Configure and hold it in memory only.
- *An S3-compatible state backend with leased locks.* OVH Object Storage
  speaks S3. The controller's state has to live off the cluster it manages,
  and its lock has to expire if the pod holding it dies.

Tickets touched by this document are named where they matter.

* Part 0: the shape

Two stacks, split at the trust boundary, both keyed by environment:

| Stack          | Runs from                 | Owns                                                   |
|----------------+---------------------------+--------------------------------------------------------|
| =ovh.infra[env]= | CI, batch, =role = "bootstrap"= | vRack network, subnet, gateway, MKS cluster, node pools, the managed Postgres, the state bucket, the controller's Deployment |
| =shop.app[env]=  | the controller, in the cluster | the app's namespace, Deployment, Service, HPA, PDB, network policies, the DB Secret |

The controller never runs =ovh.infra=: it would be able to delete the
nodes it runs on. The app stack reads what it needs from the infra stack's
outputs, and nothing flows the other way.

repo/                              a project (docs/layout.md)
  dform.toml                       its root
  stacks/infra.df                  the ovh.infra[env] stack
  stacks/app.df                    the shop.app[env] stack
  modules/app.df                   the app, as a module
  policies/ovh.df                  change-management policy for both stacks
  config/ovh.infra/prod.yaml       per-env configuration rows (data tables ticket)
  providers/ovh/                   the bridged schema, as facts
#+end_example

* Part 1: what the OVH schema has to say

The provider publishes these as schema facts; they are the assumptions the
rest of the document leans on. Only the lines that change behaviour are
shown. =force_new= means a change replaces the object; =type_replace= says
which order a replacement may take.

* Part 3: the app on the cluster

The app is a module, so a second service is one =instance= line. It knows
nothing about OVH: the only OVH-shaped thing it sees is that a
=LoadBalancer= Service gets an external IP some minutes after creation,
which is an open null like any other.

#+begin_src dform
# modules/app.df

edition 2026

module app {
  input name: string
  input image: string
  input replicas: int
  input port: int
  input db_secret: string
  input pool: string                        # the node pool label to run on
  output url: string

  resource k8s.namespace ns {
    metadata.name = name
    metadata.labels = { "pod-security.kubernetes.io/enforce": "restricted" }
  }

  resource k8s.deployment web {
    metadata.name = name
    metadata.namespace = ns.metadata.name
    spec.replicas = replicas
    spec.strategy = { rollingUpdate: { maxUnavailable: 0, maxSurge: 1 } }
    spec.selector.matchLabels = { app: name }
    spec.template.metadata.labels = { app: name }
    spec.template.spec.nodeSelector = { pool: pool }
    spec.template.spec.topologySpreadConstraints = [{
      maxSkew: 1, topologyKey: "kubernetes.io/hostname",
      whenUnsatisfiable: "ScheduleAnyway", labelSelector: { matchLabels: { app: name } }
    }]
    spec.template.spec.containers = [{
      name: "web",
      image: image,
      ports: [{ containerPort: port, protocol: "TCP" }],
      envFrom: [{ secretRef: { name: db_secret } }],
      readinessProbe: { httpGet: { path: "/healthz", port: port } },
      resources: { requests: { cpu: "250m", memory: "256Mi" }, limits: { memory: "512Mi" } }
    }]
  }

  # A LoadBalancer Service: OVH provisions an Octavia load balancer; its IP
  # is an open null until then. OVH-specific annotations would go here.
  resource k8s.service web {
    metadata.name = name
    metadata.namespace = ns.metadata.name
    spec.type = "LoadBalancer"
    spec.selector = { app: name }
    spec.ports = [{ port: 443, targetPort: port, protocol: "TCP" }]
  }

  resource k8s.poddisruptionbudget web {
    metadata.name = name
    metadata.namespace = ns.metadata.name
    spec.minAvailable = 1
    spec.selector.matchLabels = { app: name }
  }

  resource k8s.horizontalpodautoscaler web {
    metadata.name = name
    metadata.namespace = ns.metadata.name
    spec.scaleTargetRef = { apiVersion: "apps/v1", kind: "Deployment", name: web.metadata.name }
    spec.minReplicas = replicas
    spec.maxReplicas = replicas * 4
    spec.metrics = [{ type: "Resource", resource: { name: "cpu", target: { type: "Utilization", averageUtilization: 70 } } }]
  }

  resource k8s.networkpolicy default_deny {
    metadata.name = "default-deny"
    metadata.namespace = ns.metadata.name
    spec.policyTypes = ["Ingress", "Egress"]
  }

  output url = "https://{web.status.loadBalancer.ingress[0].ip}"
}

* Part 4: continuous delivery

A deploy is a commit to =env/prod:release.yaml=:

#+begin_src yaml
- service: shop
  image: ghcr.io/shop/shop@sha256:9f2c...
  replicas: 3
#+end_src

The controller polls the ref, pins the commit it read, plans, gates on
policy, applies, and writes every step to the audit log. Policy decides
what needs a human:

#+begin_src dform
# policies/ovh.df: change management for both stacks.

edition 2026

policy change_management {
  # Prod changes to running software need a signed approval of the exact
  # plan (approvals ticket: the token signs the plan digest).
  requires_approval(d, "prod rollout") if {
    env == "prod"
    deformation(k, k8s.deployment, d, _)
    k != "delete"
  }

  # Any replacement or deletion of cluster or network objects needs one,
  # in any env: these are the changes that can take the platform down.
  requires_approval(d, "replaces platform infrastructure") if {
    deformation(k, t, d, _)
    k == "replace" or k == "delete"
    t in [ovh.cloud_project_kube, ovh.cloud_project_network_private,
          ovh.cloud_project_network_private_subnet]
  }

  # And the cluster itself is never deleted in prod by a plan.
  lifecycle(ovh.cloud_project_kube, "main", "prevent_destroy") if env == "prod"
  lifecycle(ovh.cloud_project_database, "pg", "prevent_destroy") if env == "prod"

  deny "image not pinned by digest" { resource: d } if {
    d in k8s.deployment
    some c in d.spec.template.spec.containers
    not matches(c.image, "@sha256:[0-9a-f]{64}$")
  }
}
#+end_src

* Part 5: changing Kubernetes while it runs

Every change to the cluster falls into one of four classes, and the
schema facts of Part 1 decide which one dform plans. The controller runs
on the cluster being changed, but it never applies these changes: they
come from CI through =ovh.infra=, and the controller only has to survive
them.

| Change                       | Schema says                  | dform plans                  | OVH does                                  |
|------------------------------+------------------------------+------------------------------+-------------------------------------------|
| pool size, autoscaler range  | in place; size ignored       | an update, or nothing        | adds or removes nodes                     |
| Kubernetes minor version     | in place                     | one update on the cluster    | rolling upgrade, draining node by node    |
| node flavor, anti-affinity   | =force_new=, =create_first=  | a new pool, then the old one | builds nodes; drains and deletes the old  |
| network, subnet, proxy mode, region | =force_new=, =destroy_first= | a replace, refused in prod | deletes the cluster and everything in it |

** 5.1 Size

Nothing to design. =min_nodes= and =max_nodes= update in place, and the
autoscaler's =desired_nodes= is ignored on both sides (Part 2), so its
movements are never drift and never planned back.

** 5.2 Upgrading Kubernetes

A version bump in =config= is one in-place update on the cluster and
nothing else in the plan: the pools, the namespace and the controller are
unchanged, because nothing they carry depends on the version. OVH upgrades
the control plane, then replaces nodes one at a time under
=update_policy = "MINIMAL_DOWNTIME"=, evicting pods through their
disruption budgets.

OVH upgrades one minor version at a time. That is a rule about the change,
not about the value, so it reads the live version and compares:

#+begin_src dform
minor(v) = to_int(split(v, ".")[1])

deny "upgrade Kubernetes one minor version at a time" { from: live, to: want } if {
  live = world.ovh.cloud_project_kube["main"].version
  want = cfg.kube
  minor(want) - minor(live) > 1
}
deny "Kubernetes versions only go up" { from: live, to: want } if {
  live = world.ovh.cloud_project_kube["main"].version
  want = cfg.kube
  minor(want) < minor(live)
}
#+end_src

=minor(v) = ...= as a function definition is not in the grammar; today it
is a relation =minor(v, m) if m = to_int(split(v, ".")[1])= and a join.

While the upgrade runs, the API server blinks and the controller's node is
drained. What makes that survivable is already in the executor, plus the
two missing pieces from the preface:

- the controller's pod is rescheduled onto an upgraded node; its
  Deployment uses =Recreate=, so two controllers never overlap;
- its state is in Object Storage, not on the node, and its lock is a lease
  that expires, so the new pod can take over from a dead one (*S3 backend
  with leased locks: not implemented*);
- identity is persisted after every Apply call, and an interrupted tick
  resumes where it stopped (landed);
- reads that fail while the API server restarts are retried per
  =type_retry= and are not drift (landed).

** 5.3 Replacing a node pool without a gap

Changing a pool's flavor forces a replacement. The schema lets the new
pool be created first, but "first" only orders the two API calls: OVH would
start draining the old nodes while the new ones are still booting. The
safe version keeps the old pool until the new one has capacity. With pools
as config rows and a generation per row, that is two rules, not an
executor feature:

#+begin_src yaml
# config/ovh.infra/prod.yaml: the new flavor, one generation up.
- { name: general, flavor: b3-32, min: 3, max: 12, generation: 2 }
- { name: batch,   flavor: c3-8,  min: 0, max: 6,  generation: 1 }
#+end_src

#+begin_src dform
# stacks/infra.df, replacing the nodepool block of Part 2.

# A generation is up when it has at least its minimum of nodes.
pool_up(n, g) if {
  pool(n, _, min, _, g)
  ovh.cloud_project_kube_nodepool["{n}-g{g}"].available_nodes >= min
}

# The target generation, always.
pool_row(n, f, mn, mx, g) if pool(n, f, mn, mx, g)

# The previous generation, as it exists in the world, until the target is up.
pool_row(n, f, mn, mx, prev) if {
  pool(n, _, mn, mx, g)
  prev = g - 1
  f = world.ovh.cloud_project_kube_nodepool["{n}-g{prev}"].flavor_name
  not pool_up(n, g)
}

resource ovh.cloud_project_kube_nodepool "{name}-g{generation}" {
  for pool_row(name, flavor, min, max, generation)
  # ... fields as in Part 2 ...
}
#+end_src

  pending group: delete of general-g1, may derive after tick 1 (reads pool_up(general, 2))
  apply + general-g2                                        ok  4m12s
  boundary: available_nodes of general-g2 := 3
tick 2: plan: 1 deformation (1 delete)
  - ovh.cloud_project_kube_nodepool.general-g1
  apply - general-g1                                        ok  6m40s   (OVH drains 3 nodes)
stack ovh.infra[env=prod] is undeformed
#+end_example

The pods move because both generations carry the label =pool: general=
that the app's =nodeSelector= asks for, and the disruption budget keeps at
least one replica up while OVH drains. The controller is evicted with
everyone else and resumes on the new pool.

This is the pattern the design was built for: the rollout order is data
and rules over the live world, it shows up in the plan as a pending group
before anything happens, and nothing in the executor knows what a node
pool is.

** 5.4 Changes that replace the cluster

A new VLAN, subnet, kube-proxy mode or region forces a new cluster, and
MKS cannot create a second cluster with the same name, so the replacement
is destroy-first: everything running on it is lost. dform's answer today:

#+begin_example
plan: 1 deformation (1 replace), 5 pending
  -/+ ovh.cloud_project_kube.main    (replace: kube_proxy_mode "ipvs" -> "iptables")
denied:
  lifecycle prevent_destroy: the plan would delete ovh.cloud_project_kube.main
needs approval:
  ovh.cloud_project_kube.main        replaces platform infrastructure
#+end_example

That stops the accident, but it does not show the damage. The plan names
the five objects of =ovh.infra= that ride on the cluster (the namespace,
the secret, the controller), and not one of the app stack's, because the
app stack's dependence on the cluster is not a relation anywhere: its
=provider k8s {}= is simply "the cluster I am running in". A cross-stack
blast radius needs the app stack to say which cluster it targets, for
example =provider k8s { cluster = stack_output(infra, "cluster_id") }=, so
a replacement upstream shows downstream as "every object recreated". That
is new work, not a ticket yet.

The real answer is not to replace a production cluster in place. Keyed
stacks make the alternative ordinary: put the cluster generation in the
key.

#+begin_src dform
stack ovh.infra[env, cluster] { role = "bootstrap" }
input cluster: enum("a", "b")
#+end_src

=ovh.infra[env=prod, cluster=b]= is a second, independent deployment with
its own network, pools and controller. Run the app stack against it, move
traffic at DNS, then =dform stack handover= the app stack to the new
controller and destroy =cluster=a= with an approval. Every step is an
ordinary plan. The collision lint from the keyed-stacks ticket checks that
the two clusters' names differ, and =isolated= stays off, because both live
in the same OVH project.

* Part 6: running it

Not all at once. Each environment has a one-time setup, one batch apply
from CI, and after that, deploys are git commits. Every =apply= is one
command that runs all of its ticks and stops early only on a deny, a
missing approval, or =--max-ticks=.

** Once per OVH project

1. Create the Public Cloud project and attach it to a vRack (OVH console).
2. Create API credentials for the provider, scoped to the project, and give
   them to CI: =OVH_ENDPOINT=, =OVH_APPLICATION_KEY=,
   =OVH_APPLICATION_SECRET=, =OVH_CONSUMER_KEY= (the names the =ovh/ovh=
   provider reads; the bridge passes them through Configure).
3. The state bucket. =ovh.infra= keeps its state in Object Storage, but it
   cannot create the bucket its own state lives in. Either create
   =dform-state= by hand, or run the first apply with a local backend and
   move the state afterwards with =dform stack handover= (below).

** Once per environment: the infrastructure

#+begin_src sh
# Review, then apply. Three ticks: network, cluster and database; pools,
# namespace and state secret; the controller once a pool has nodes.
dform --file stacks/infra.df plan  --set env=dev --set project=$OVH_PROJECT
dform --file stacks/infra.df apply --set env=dev --set project=$OVH_PROJECT

# If the first apply used a local backend: move the state into the bucket.
dform stack handover 'ovh.infra[env=dev]' --to 's3("dform-state", "infra/dev")'
#+end_src

For prod, CI plans on a pull request and applies the saved plan after
approval, so what was reviewed is what runs:

#+begin_src sh
dform --file stacks/infra.df plan --set env=prod --set project=$OVH_PROJECT --out plan.json
# ... the approval service shows the plan, collects the checkmark, returns a token ...
dform apply plan.json --approval token.jws
#+end_src

** The app: nothing to run

Tick 3 of the infra apply started the controller in the cluster. It runs
=shop.app[env=dev]=, starts from empty state in the bucket, reads
=env/dev:release.yaml= from the deploys repository, and deploys it. There
is no first app apply to run by hand; watching it is
=kubectl -n dform-system logs deploy/dform-controller -f=, or =dform log=
against the app stack's audit log.

** Day two

| To                                  | Do                                                      |
|-------------------------------------+---------------------------------------------------------|
| deploy a release                    | commit =release.yaml= on =env/<env>= in the deploys repo |
| approve a prod release              | the approval service drops the token the controller asked for |
| roll back                           | =git revert= that commit                                |
| resize pools, upgrade Kubernetes    | edit =config/ovh.infra/<env>.yaml=, then the CI plan and apply of =ovh.infra= |
| replace a pool's flavor             | bump its =generation= in the config (Part 5.3)          |
| see why something is the way it is  | =dform why ...= against either stack                    |
| check nothing was tampered with     | =dform log verify=                                      |

The only commands a human runs after bootstrap are the CI ones for
=ovh.infra=, and those are the changes that can hurt the platform, so they
are the ones that stay batch, reviewed and approved.
